# Практична робота №2. Варіант 6. Data Analysis: Sales Dashboard

## Опис проєкту
Цей проєкт реалізує мультиагентну систему MAS для аналізу продажів і підготовки управлінських висновків. Використано архітектуру Supervisor. Проєкт демонструє інтеграцію з локальним MCP-сервером, реалізацію безпекових механізмів (Guardrails) та впровадження HITL для ризикових операцій. Реалізація виконана у двох фреймворках LangGraph та CrewAI.

## 1. Архітектура
*   **Патерн координації:** Supervisor (у LangGraph) / Hierarchical Process (у CrewAI).
*   **Агенти та інструменти:**
    *   `data_loader` — інструмент: `load_sales_data`
    *   `sales_analyst` — інструмент: `calculate_kpis`
    *   `anomaly_detector` — інструмент: `detect_sales_anomalies`
    *   `report_reviewer` — інструмент: `export_dashboard`
*   **Ризиковий інструмент:** `export_dashboard` - вимагає ручного підтвердження HITL перед публікацією звіту.

## 2. Безпековий аналіз (Guardrails)
У файлі `guardrails.py` реалізовано 3 рівні захисту:
1.  **Input Guardrail (Injection Detection):** Перевіряє ввід користувача на наявність спроб обійти інструкції (наприклад, фрази типу "ignore previous instructions").
2.  **Tool Guardrail (Allowlist):** Жорстко обмежує доступ агентів до інструментів. Наприклад, `data_loader` не може викликати `export_dashboard`, що запобігає privilege escalation.
3.  **Output Guardrail (PII Redaction):** Перехоплює фінальну відповідь перед відправкою користувачу і маскує чутливі дані (наприклад, замінює email-адреси на `[REDACTED EMAIL]`).

## 3. Відповіді на аналітичні питання
*   **Чому supervisor-патерн доцільний для системи аналітики продажів?**
    Дані не можна аналізувати, поки їх не завантажили, а дашборд не можна експортувати до розрахунку аномалій. Supervisor гарантує цей контроль маршрутизації та не дозволяє агентам хаотично передавати дані одне одному.
*   **Як tool guardrail (allowlist) запобігає privilege escalation?**
    Якщо хакер зламає промпт агента `data_loader` і змусить його експортувати звіт, `tool_guardrail` заблокує цю дію на рівні Python-коду, оскільки `data_loader` не має `export_dashboard` у своєму списку дозволених інструментів.
*   **Чому export_dashboard є ризиковим інструментом і потребує HITL?**
    Публікація дашборду може означати відправку звіту стейкхолдерам або клієнтам. Якщо LLM зробила помилку в розрахунках, автоматичний експорт призведе до репутаційних чи фінансових втрат. Людина повинна верифікувати висновок.
*   **Які guardrails доцільно додати?**
    Слід додати "Semantic Validation Guardrail" на виході, який би перевіряв звіт на наявність фраз "я не зміг порахувати" або "дані відсутні", і блокував би експорт таких "пустих" звітів.

## 4. Порівняльна таблиця (LangGraph vs CrewAI)

| Критерій | LangGraph | CrewAI |
| :--- | :--- | :--- |
| **LOC (рядки коду)** | ~120 (більш багатослівний) | ~80 (лаконічніший) |
| **Рівень контролю (1-5)** | 5 (повний контроль над станом і графом) | 3 (багато приховано "під капотом") |
| **Зручність debugging (1-5)** | 5 (видно кожен крок і вузол) | 4 (гарні логи, але важко змінити логіку менеджера) |
| **Складність handoff реалізації** | Висока (треба вручну писати логіку переходу) | Низька (менеджер робить це автоматично) |
| **HITL реалізація** | Нативна, зручна (через `interrupt`) | Складна (не має прямого аналога `interrupt` для зупинки графа) |

## 5. Інструкція з запуску
1.  **Встановлення залежностей:** `pip install -r requirements.txt`
2.  **Налаштування середовища:** Створіть файл `.env` та додайте `OPENROUTER_API_KEY`, а також ключ для LangSmith (`LANGCHAIN_API_KEY`, `LANGCHAIN_TRACING_V2=true`).
3.  **Запуск тестів:** Виконайте `pytest test_project.py -v > pytest_results.txt` для перевірки інструментів та генерації звіту про тестування.
4.  **Запуск LangGraph:** Виконайте `python langgraph_mas.py`. Лог одного з таких успішних виконань збережено у `trace.json`
5.  **Запуск CrewAI:** Виконайте `python crewai_mas.py`

## 6. Результати observability та тестування
*   **trace.json:** Файл містить експортований запис виконання trace з LangSmith. Він документально підтверджує коректну маршрутизацію між агентами (`data_loader` -> `sales_analyst` -> `anomaly_detector` -> `report_reviewer`), виклики MCP-інструментів та зупинку графа для HITL підтвердження.
*   **pytest_results.txt:** Файл містить консольний вивід виконання 6 тестів. Усі тести пройдено успішно зі статусами `PASSED`, що гарантує безпеку та стабільність інструментів до їх виклику агентами.
